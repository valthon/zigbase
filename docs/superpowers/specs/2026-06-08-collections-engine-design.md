# ZigBase Sub-Project 2: Collections & Schema Engine — Design

**Date:** 2026-06-08
**Status:** Approved (design); implementation plan to follow
**Depends on:** Sub-Project 1 (Foundation) — merged to `main`.
**Builds toward:** Sub-Project 3 (Records CRUD + query language), which consumes this engine.

---

## 1. Overview & Goals

Sub-Project 2 makes ZigBase's collections real: user-defined, dynamically-schema'd tables
created and altered at runtime. It delivers a typed field model, a schema engine that maps
collections to physical SQLite tables (with safe in-place migrations), a system-migration
runner, and an **unprotected** REST API for managing collections. Record CRUD over these
collections is Sub-Project 3.

Per design decisions made during brainstorming, SP2 takes the robust path: **full relation
fields** (with SQLite foreign keys for single relations), **full table-rebuild schema diffing**
(stable field IDs enable safe renames and type changes), and **REST management now**
(`/api/collections`, auth-gating deferred to SP5).

### In scope
- System tables + migration runner (`_collections`, `_migrations`).
- Field model for all types (relation full; file stubbed as filename text until SP8).
- Schema engine: create / get / list / update (rebuild) / delete collections.
- DDL generation + the table-rebuild migration plan.
- REST collection-management API (unprotected).
- Foundation refactors required to support the above: an `App` context threaded through
  `RequestCtx`, a real path-param router, an extended error envelope, extra `Stmt` column
  helpers, and an id generator.

### Out of scope (later sub-projects)
- Record CRUD, query/filter language, multi-relation cascade at delete time (SP3).
- API access rules enforcement (SP4) — rule columns are stored but unused.
- `auth`/`view` collection types (SP5+) — the `type` field exists; only `base` is functional.
- Real file storage (SP8) — `file` fields store filename text only.
- Superuser authorization on the management API (SP5) — endpoints are open, with a TODO.
- User-authored data migration files — `_collections` is the source of truth.

## 2. System Tables

Created by migration `0001_init`.

### `_collections`
| Column | Type | Notes |
|---|---|---|
| `id` | TEXT PK | 15-char generated id |
| `name` | TEXT UNIQUE | collection name = physical table name; validated identifier |
| `type` | TEXT | `base` (only functional value in SP2); `auth`/`view` reserved |
| `system` | INTEGER | 1 for built-in/system collections, 0 otherwise |
| `schema` | TEXT | JSON array of field definitions (see §3) |
| `indexes` | TEXT | JSON array of index definitions (see §4) |
| `listRule` `viewRule` `createRule` `updateRule` `deleteRule` | TEXT NULL | stored, **unused until SP4** |
| `created` `updated` | TEXT | RFC3339 |

### `_migrations`
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER PK | autoincrement |
| `name` | TEXT UNIQUE | e.g. `0001_init` |
| `applied_at` | TEXT | RFC3339 |

### User collection tables
Each collection becomes a physical table named exactly `name`, with system columns first:
- `id` TEXT PRIMARY KEY (15-char)
- `created` TEXT, `updated` TEXT (RFC3339)
- one column per field (§3).

## 3. Field Model

A collection's `schema` is a JSON array of fields. Each field:

```jsonc
{
  "id": "f8x2k9qa",          // stable 8-char id — survives renames
  "name": "price",           // column name; validated identifier, unique within collection
  "type": "number",
  "required": false,
  "unique": false,           // when true, engine emits a UNIQUE index
  "options": { ... }         // type-specific (see table)
}
```

The **stable field `id`** is the linchpin of safe migrations: the rebuild diff (§5) matches
old vs new fields by `id`, so a renamed field preserves its data (it is not seen as
drop+add). IDs are generated by the engine when a field is first created and never change.

### Types, SQLite column mapping, and options

| `type` | SQLite column | `options` |
|---|---|---|
| `text` | TEXT | `min`,`max` (length), `pattern` (regex string) |
| `email` | TEXT | `exceptDomains`,`onlyDomains` (optional string arrays) |
| `url` | TEXT | — |
| `editor` | TEXT | — (HTML) |
| `date` | TEXT (RFC3339) | `min`,`max` (RFC3339 bounds, optional) |
| `autodate` | TEXT (RFC3339) | `onCreate` (bool), `onUpdate` (bool) — engine/records set the value |
| `bool` | INTEGER (0/1) | — |
| `number` | REAL or INTEGER (by `mode`) | `mode`,`scale`,`min`,`max` (see below) |
| `json` | TEXT | `maxSize` (bytes, optional) |
| `select` | TEXT (single) / TEXT JSON-array (multi) | `values` (string[]), `maxSelect` (≥1) |
| `relation` | TEXT id (single) / TEXT JSON-array (multi) | `targetCollectionId`, `cascadeDelete` (bool), `minSelect`,`maxSelect` |
| `file` | TEXT filename (single) / TEXT JSON-array (multi) | `maxSelect`,`maxSize`,`mimeTypes` — **stub**, real storage in SP8 |

A field with `maxSelect == 1` (select/relation/file) is single-valued; `> 1` is multi-valued
(stored as a JSON array of strings).

### Number `mode` (float / int / fixed)
`number.options.mode` selects numeric behavior:

| `mode` | SQLite column | Semantics |
|---|---|---|
| `float` (default) | REAL | IEEE-754 double. Fast; **may lose precision** — documented platform tradeoff. |
| `int` | INTEGER | Whole numbers only; non-integer input rejected. |
| `fixed` | INTEGER | Fixed-point. `scale` (1–8) decimal places. Value stored as `round(value × 10^scale)`. Example `scale=2`: `10.50` ⇒ stored INTEGER `1050`. |

**Precision note (binds SP3):** for `fixed`, record (de)serialization must convert using
**exact decimal-string arithmetic**, not an `f64` multiply — i.e. parse the incoming decimal
string `"10.50"` and the `scale` to produce the integer `1050` directly, and format the stored
integer back to a decimal string on read. This preserves full precision. SP2 only declares the
schema, validates options (`mode` ∈ {float,int,fixed}; `scale` ∈ 1..8 required iff
`mode==fixed`), and maps `fixed`/`int` ⇒ INTEGER, `float` ⇒ REAL. The conversion itself is
implemented with records in SP3.

### Validation (engine-enforced on create/update)
- **Collection name:** non-empty, matches `^[A-Za-z][A-Za-z0-9_]*$`, not starting with `_`,
  not a reserved system name, unique (case-insensitive).
- **Field name:** matches the same identifier pattern, unique within the collection
  (case-insensitive), not colliding with system columns `id`/`created`/`updated`.
- **Type/options:** `type` is known; options validated per type (e.g. `select` requires a
  non-empty `values`; `relation.targetCollectionId` must reference an existing collection;
  `number` mode/scale as above).
- Validation failures produce field-keyed errors in the response envelope (§7).

## 4. Indexes

`_collections.indexes` is a JSON array of index definitions:
```jsonc
{ "name": "idx_price", "fields": ["price"], "unique": false }
```
The engine generates `CREATE [UNIQUE] INDEX "<name>" ON "<table>" ("<f1>","<f2>")`. A field
with `unique: true` (§3) is sugar that contributes an implicit unique index. Indexes are
(re)created after the table on create and after each rebuild.

## 5. Schema Engine & DDL

Two modules with a clean split:

### `ddl.zig` — pure SQL generation (no DB access; heavily unit-tested)
- `createTableSql(collection) -> []u8`: system columns + field columns + inline
  `FOREIGN KEY` clauses for single-value relations
  (`ON DELETE CASCADE` if `cascadeDelete` else `ON DELETE SET NULL`).
- `createIndexSql(table, index) -> []u8`.
- `columnDef(field) -> []u8`: one field's `"name" TYPE` fragment.
- `rebuildPlan(oldCollection, newCollection) -> []const []u8`: the ordered statement list for
  an update (see below).

### `collections.zig` — the engine (orchestrates ddl + db + persistence)
Operating on the writer connection inside transactions:
- `create(app, def) -> Collection`: validate → assign ids (collection id, field ids) →
  `CREATE TABLE` + indexes → insert `_collections` row. All-or-nothing in one transaction.
- `get(app, idOrName) -> ?Collection`, `list(app) -> []Collection`: read `_collections`,
  parse `schema`/`indexes` JSON.
- `update(app, idOrName, newDef) -> Collection`: load current, compute diff by field id,
  execute the **rebuild plan**, update the `_collections` row. One transaction.
- `delete(app, idOrName)`: refuse with a validation error if any other collection has a
  relation whose `targetCollectionId` is this collection; else `DROP TABLE` + delete row.

### The rebuild plan (update = generalized SQLite "12-step")
Always rebuild (simple and always correct). Within one transaction, with `foreign_keys`
temporarily disabled around the swap (`PRAGMA foreign_keys=OFF;` … `ON;`):
1. `CREATE TABLE "<name>__new" ( <new schema> )`.
2. `INSERT INTO "<name>__new" (<new cols>) SELECT <mapped old cols / CAST / NULL> FROM "<name>"`.
   Column mapping is **by field id**: retained fields copy (with `CAST` when the SQLite type
   changed); new fields get default/NULL; removed fields are dropped. System columns always
   copy.
3. `DROP TABLE "<name>"`.
4. `ALTER TABLE "<name>__new" RENAME TO "<name>"`.
5. Recreate all indexes for the new schema.

`foreign_keys` is re-enabled at the end; an integrity check (`PRAGMA foreign_key_check`) may be
run before commit to surface broken references.

## 6. Migrations Runner — `migrations.zig`

- Ensures `_migrations` exists (bootstrap), then runs an **ordered list of Zig migrations**,
  each `{ name, up(writer: *Db) !void }`, skipping any already recorded, each inside a
  transaction; records `name` + `applied_at` on success.
- `0001_init` creates `_collections` (and any other system tables).
- Invoked on `serve` startup (before listening) and by a new CLI command **`zigbase migrate`**
  (runs pending migrations and exits).
- Collection schema changes are **not** migration entries — `_collections` is authoritative.

## 7. REST API & Required Foundation Refactors

### New/changed infrastructure
- **`app.zig`** — `App { allocator, pool: *db.Pool }` (config/auth added later). Owns shared
  request-handling state. Created in `runServe`, passed to the server.
- **`RequestCtx`** gains `app: *App` and `params: std.StringHashMap([]const u8)` (path
  params). Replaces the `Server.instance` global as the way handlers reach the DB.
- **`router.zig`** — registers `(method, pattern, handler)`; matches a request path by
  splitting on `/`, capturing `:name` segments into `params`; falls back to 404. Replaces the
  `if`-chain in `server.zig`. `server.zig`'s `onRequest` builds the `RequestCtx` (with `app`
  and parsed params) and dispatches through the router.
- **`api/error.zig`** — `ApiError` extended to carry optional field errors:
  `data: ?std.StringHashMap(FieldError)` where `FieldError{ code, message }`; envelope becomes
  `{code,message,data:{<field>:{code,message}}}` (empty `{}` when none). New constructors:
  `badRequest`, `notFound`, `conflict`, `validation(fields)`, `internal`.
- **`db.Stmt`** — add `columnDouble(idx) f64`, `columnType(idx) enum{Null,Integer,Float,Text,Blob}`,
  `isNull(idx) bool` (needed to read REAL/dynamic columns).
- **`setZapStatus`** — extend to map 200, 201, 400, 404, 409, 422, 500.
- **`id.zig`** — `generate(buf, len)` producing URL-safe ids; helpers `collectionId()`
  (15-char) and `fieldId()` (8-char). Uses a CSPRNG seed; varies per call.

### Endpoints — `api/collections.zig` (pure handlers; **unprotected**, `// TODO(SP5): superuser`)
| Method & path | Behavior | Success |
|---|---|---|
| `GET /api/collections` | list all | 200, JSON array |
| `POST /api/collections` | create from body | 201, the created collection |
| `GET /api/collections/:idOrName` | fetch one | 200 / 404 |
| `PATCH /api/collections/:idOrName` | update (rebuild) | 200 / 404 |
| `DELETE /api/collections/:idOrName` | delete | 204 / 404 / 409 (referenced) |

A `Collection` serializes to JSON as `{id,name,type,system,schema:[...],indexes:[...],
listRule,...,created,updated}`.

### Data flow
`zap → server.onRequest (build RequestCtx{app, params}) → router → pure handler →
collections engine → db (writer/reader)`.

## 9. Error Handling

All failures return the JSON envelope (§7). Validation errors populate `data` with per-field
`{code,message}` (e.g. `name: {code:"validation_not_unique", message:"..."}`). Engine errors
map to HTTP: validation → 400/422, missing → 404, relation-referenced delete or duplicate name
→ 409, unexpected → 500. SQL is always parameterized or built from **validated identifiers**
(names that already passed the identifier regex), never from raw untrusted input.

## 10. Testing Strategy

- **Unit:** `id` (length/charset/variation); `schema` validation (valid + each invalid case);
  `ddl` string generation (CREATE TABLE for each type, FK clauses, indexes); `rebuildPlan`
  diff (add / remove / rename-by-id / type-change → expected statement list); number-mode
  option validation.
- **Engine (temp DB):** create → table + columns exist with right SQLite types; update adding
  a field → column added, existing rows preserved; **rename a field → data preserved** (the
  field-id payoff); type change → values CAST; delete → table gone; delete-while-referenced →
  error.
- **Migrations:** runner applies `0001_init` once, is idempotent on re-run, records rows.
- **Handlers (pure, temp App):** each endpoint's status + JSON for success and error paths,
  including validation `data`.
- **Manual smoke:** curl the full lifecycle — create a collection with several field types,
  list, get, PATCH to add/rename a field, DELETE — against a running `zigbase serve`.

TDD throughout; `zig build test` stays green at each step.

## 11. Risks & Notes

- **Rebuild cost:** always-rebuild on update is O(rows). Acceptable now (schema changes are
  rare, datasets small); a future optimization may use direct `ALTER` for additive-only diffs.
- **Relation FK + rebuild:** dropping/renaming a table that other tables reference by FK
  requires the `foreign_keys=OFF` window during the swap and a `foreign_key_check` before
  commit; multi-relation cascade is deferred to SP3 record-delete logic.
- **Router/App refactor touches Foundation `server.zig`/`http.zig`/`main.zig`:** intentional,
  enacting the Foundation review's forward-looking notes; existing 19 tests must stay green.
- **Unprotected management API:** acceptable only until SP5; every collections endpoint carries
  a `// TODO(SP5): require superuser` marker.
