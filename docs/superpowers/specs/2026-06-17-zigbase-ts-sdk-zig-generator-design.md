# ZigBase TypeScript SDK — SP2.1b: Pure-Zig Client Generator

**Status:** Design approved, pending spec review
**Date:** 2026-06-17
**Scope:** Sub-project SP2.1b — the pure-Zig generator that emits a tailored `zbase.gen.ts`
from a ZigBase app's comptime `.collections`, instantiating the SP2.1a typed core. Builds on
SP2.1a (the typed core `@zigbase/client/typed`, merged via PR #19). SP2.2 (typed RPC + framework
typed-routes) follows.

## Context & strategy

The ZigBase client SDK is three tiers (base SP1 → bespoke comptime SP2 → derived runtime SP3).
SP2 is the flagship comptime-generated client, decomposed into:

- **SP2.1a (shipped):** the hand-written generic typed core `@zigbase/client/typed` + a
  hand-authored `blog.gen.ts` fixture that defined the golden contract — the exact shape a
  generated client takes.
- **SP2.1b (this doc):** the **pure-Zig generator** that produces that shape automatically from
  the comptime `.collections`. The hard TypeScript already lives, tested, in the typed core; the
  generator emits only the thin, concrete per-backend layer that instantiates it.

The headline remains: *your typed client is a build artifact of `zig build`* — pure Zig, no Node
in the generation path (Node only typechecks/tests the result).

## Design principles

1. **Pure-Zig codegen.** The generator is Zig; it runs as a `build.zig` step. Node is never
   required to generate — only to typecheck and test the emitted file.
2. **Thin output over a tested core.** The generator emits concrete types + a one-line
   `createClient` wiring; all intricate machinery (the `WithExpand` generic, `compileWhere`, the
   fluent builder, the service factory, the realtime/files helpers) is the SP2.1a typed core.
3. **Break as early as possible.** Every correctness guard fires at generation time (a failed
   `zig build` with a precise message), never at runtime or in tests.
4. **Deterministic & diffable.** Output is emitted in declared order with a header + schema hash,
   so regeneration produces clean diffs; a committed file is the norm (Prisma-style).
5. **Grounded validation.** Correctness is proven against a purpose-built coverage fixture and a
   real published example, both exercised end-to-end against a live binary.

## Architecture & components

### Generator executable (pure Zig)
New source `src/codegen/gen_client.zig` in the zigbase package. Its `main()`:
1. reads the app's parsed `[]const schema.Collection` (see "config access" below),
2. runs the **generator-time guards**,
3. walks the collections through **emit-helpers** — one Zig fn per TS fragment (`emitImports`,
   `emitRecord`, `emitCreate`, `emitUpdate`, `emitWhere`, `emitFields`, `emitRelations`,
   `emitExpandKeys`, `emitService`, `emitRealtimeAlias`, `emitMeta`, `emitClientFactory`), backed
   by a shared **field → TS type mapper**,
4. writes `zbase.gen.ts`.

CLI flags:
- `--out <path>` — output file path.
- `--api-prefix <p>` — default `/api` (reserved for path-derived needs; collections don't need it,
  but it keeps the generator forward-compatible with SP2.2 routes).
- `--check` — re-emit to a buffer and diff against the file at `--out`; exit non-zero on drift,
  write nothing. The CI staleness guard.

### Config access — the `pub const App` convention
The generator reads the schema from the consumer's module via `@import("app").App.collections`
(`provision.buildCollections` already produced `[]const schema.Collection` at comptime, with
relation `targetCollectionId` holding the target collection **name** at this stage — so no id→name
resolution is needed). This requires the consumer to expose the app type at module scope:
```zig
pub const App = zigbase.App(.{ .collections = .{ … }, … });
pub fn main(init: std.process.Init) !void { return App.runCli(init); }
```
This is a small, clean structural convention, documented as the codegen prerequisite. It does not
change the runtime behavior of the app.

### Build helper — `genClientStep`
zigbase exposes from its `build.zig`:
```zig
pub fn genClientStep(b: *std.Build, zigbase_dep: *std.Build.Dependency,
                     app_mod: *std.Build.Module, opts: GenOpts) *std.Build.Step.Run
```
It builds the generator exe with `app_mod` (the consumer's module exposing `pub const App`) and
zigbase imported, then runs it writing `opts.out`. The consumer wires `zig build gen-client` to it
(and optionally `zig build gen-client-check` → the exe with `--check` for CI).

### Output
A single committed `zbase.gen.ts` importing `@zigbase/client` + `@zigbase/client/typed`, with a
`// generated by zigbase — do not edit` header + a schema hash. Emitted in declared order.

## What it emits & mapping rules

For each collection, the generator emits the concrete shapes the SP2.1a hand-authored fixture
contains, derived mechanically from `schema.Collection`/`Field`:

### Field → TS mapping
| `FieldType` | TS |
| --- | --- |
| `text`/`email`/`url`/`editor` | `string` |
| `number` | `number` |
| `bool` | `boolean` |
| `date`/`autodate` | `string` (ISO) |
| `json` | `unknown` |
| `select` | string-literal union of `.values` (array if `isMultiValue()`) |
| `relation` | `string` id (array if multi) + a typed expand edge to the target record |
| `file` | `string` filename (array if multi) |

`field.isMultiValue()` (maxSelect > 1 on select/relation/file) selects the array form. `id`,
`created`, `updated` are always present on reads. For `.type == .auth` collections the generator
synthesizes the **visible** system fields (`email`, `username`, `verified`); `passwordHash`/
`tokenKey` are `hidden` and skipped.

### Per-collection emitted artifacts
- **Record** interface; **`Create`** (required required, others optional; `file`→`File | Blob`; no
  `id`/auto-dates/read-only system fields); **`Update = Partial<Create>`**.
- **`Where`** (operator objects + `AND`/`OR` + one-level nested relation `author: string | RelOps
  | TargetWhere`); **`Fields`** (`TypedFieldExpr<V>` per field); **`Relations`** map (relation →
  target record type, via the comptime target name); **`Expand`** keys (string-literal union).
- **Concrete `*Service`** interface (`getOne<K>`/`getList<K>`/`getFirstListItem<K>`/`getPage`/
  `iterate`/`getFullList`/`create<K>`/`update<K>`/`delete`/`filter`, with expand-narrowing on the
  read + create/update paths); the per-collection **`CollectionMeta`** const; **realtime as a type
  alias** `type <Name>Realtime = RawTypedRealtime<Record, Where>`; the **files** field-typing.
- **Auth collections** (the SP2.1a carry-forwards): `Update = Partial<Omit<Create, "password" |
  "passwordConfirm">>`, `password`/`passwordConfirm` in `Create`, and `authWithPassword` (+ the
  other auth methods) grafted onto the service.
- **`createClient`** wiring: `db.*`, `realtime.*`, `files`, `authStore`, `send`, `fetch`.

The shared Zig→TS field mapper is one helper reused by every emit fn.

## Generator-time guards

Both fail the `zig build` with a precise message; neither can silently mis-emit:

1. **Operator-name invariant.** A relation-target collection with a field named like a where
   operator (`eq`/`neq`/`gt`/`gte`/`lt`/`lte`/`like`/`nlike`/`in`) makes the `where`-DSL's
   nested-relation-vs-id-operator disambiguation ambiguous → error naming the collection + field.
   (This is independent of the top-level namespacing: collections live under `db.*`, so collection
   names cannot collide with the `rpc`/`files`/etc. accessors and need no reserved-name guard.)
2. **Identifier safety & collisions.** Each collection/field name must yield a valid TS
   identifier; the generated type names (`<Name>`, `<Name>Where`, `<Name>Relations`,
   `<Name>Service`, `<Name>Fields`, select unions) must be mutually unique and must not collide
   with the typed-core's reserved/imported names (`WithExpand`, `RelOps`, `Expr`, `StringOps`, …).
   Any clash → a precise error naming the offending collection/field. Nested relation references
   pull a target's type names into another collection's scope, so cross-collection uniqueness
   matters.

## Validation & testing

Two grounded targets; neither contorts to reuse SP2.1a's blog suite.

### 1. The dating-app coverage fixture (its own distinct artifact)
A purpose-built schema — themed as a **dating app**, kept clearly separate from the published
examples — designed to exercise **every schema capability** in one coherent domain. It is its own
first-class artifact (its own directory), structured to grow (future capability tests; a possible
future "advanced" demo — out of scope now).

**Schema (full capability coverage):**
- `profiles` (**auth**): name (text), bio (**editor**), website (**url**), age (**number** int),
  gender (**select**), avatar (**file**, public) + synthesized auth/system fields.
- `photos`: owner (**relation**→profiles), image (**file**), visibility (**select** public/private),
  caption (text), tags (**relation**→tags, **multi**).
- `tags`: label (text, **unique**).
- `messages`: from + to (**two relations to the same target**, profiles), body (text), sentAt
  (**autodate** onCreate), read (**bool**).
- `winks`: from/to (relation→profiles), createdAt (autodate onCreate).
- `subscriptions`: profile (relation→profiles), plan (**select** free/plus/premium), price
  (**number** fixed/scale 2), renewsAt (**date** with min/max), active (**bool**), metadata
  (**json**).

**Tests against the generated `zbase.gen.ts`:**
- **Type-level** (`*.test-d.ts`): every field→TS mapping; expand-narrowing single + multi; all
  where operators + nested relation + `AND`/`OR`; `create`/`update` (required/optional, file→
  `File | Blob`, auth `password`/`passwordConfirm`); fluent operand typing; service signatures;
  realtime alias; file-field typing; `@ts-expect-error` negatives for each rejection.
- **Zig unit tests:** the emit-helpers, the field→TS mapper, and the guards (error cases).
- **Real-binary integration/e2e:** seed the dating schema, drive the generated client through
  CRUD, filter (incl. nested relation), expand, native cursor, realtime event, auth, and file
  upload (public + private).
- **Golden snapshot** of the generated `.ts` committed; a test diffs fresh output against it;
  **`--check`** in CI.

### 2. Golfsim — the real, customer-facing codegen example
Refactor `examples/golfsim` to the `pub const App` convention and wire `genClientStep` into its
`build.zig`, so `zig build gen-client` emits golfsim's real `zbase.gen.ts`. Validated more than
smoke: **typecheck + unit + some e2e** against the real binary, driving a few real operations
through golfsim's generated client. This grounds codegen to an actual published example.

### Blog — unchanged
`examples/blog` stays the simple "no code" showcase (precompiled backend + the dynamic base SDK).

### CI
A job/step that: builds the generator, runs `gen-client --check` for the fixture + golfsim
(staleness guard), and runs the TypeScript type + integration suites against the generated output.

## Scope / out of scope

**In:** the full SP2.1a surface generated from `.collections` — records/create/update, where +
fluent + nested relations, expand-narrowing, typed services (incl. native cursor/iterate/
getFullList), realtime/live, files, the `db.*`/`realtime.*`/`files` namespaces, auth synthesis —
plus the generator-time guards, the dating-app coverage fixture, the golfsim example wiring, and
the `--check` guard.

**Out (later):**
- **Routes & typed RPC** → SP2.2 (needs the framework route-typing change; routes carry no typed
  I/O today). The `--api-prefix` flag is reserved for it.
- **The runtime-introspection path** → SP3 (the derived, lesser-tier dynamic client).
- **Typed `json`-field payloads** (stay `unknown`).
- **Further developing the dating app into an "advanced" demo** (possible future; not now).

## Carry-forwards from SP2.1a (already settled, implemented by the generator)
- Auth `Update = Partial<Omit<Create, "password" | "passwordConfirm">>` and `authWithPassword`
  grafting, keyed off `CollectionMeta.isAuth` / `Collection.type == .auth`.
- File fields → `File | Blob` in `*Create`.
- A `relationResolver` emitted from relation targets (one level), via the comptime target name.
- Realtime emitted as `type X = RawTypedRealtime<Rec, Where>` (the generic), not a bespoke
  interface. Services stay concrete (expand-narrowing needs per-method generics + clean hovers).
