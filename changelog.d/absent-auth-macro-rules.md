### Security
- Access rules no longer let an anonymous caller, or one whose session has expired, match rows through an `@request.auth.*` comparison. The absent auth value was bound as an empty string. As a result `owner ~ @request.auth.id` compiled to `LIKE '%%'` and allowed REST list, view, update and delete on every row that had an owner. `owner != @request.auth.id`, `owner > @request.auth.id`, `owner = @request.auth.id` on rows with an empty owner, and the create rule `@request.data.owner = @request.auth.id` with no `owner` in the body were affected in the same way. An absent `@request.auth.*`, `@request.account.id` or `@request.account.role` value now behaves like SQL `NULL`. Every comparison that uses it is false, whatever the operator, and inside an `in (…)` list it matches nothing. The presence tests `@request.auth.id != ""` and `@request.auth.id = ""` keep their meaning (#505).

### Fixes
- Realtime access rules now see the subscriber's auth collection in `@request.auth.collection` and the active account's role in `@request.account.role`. Both used to be empty for WebSocket and SSE subscribers, so a rule such as `@request.auth.collection = "users"` or `@request.account.role = "editor"` denied every realtime event. Account scope is refreshed from current memberships for each delivery, so demotion or membership removal stops protected events on already-open connections. Auth hooks (`beforeAuthSuccess`, `onAuth` and the refresh/logout lifecycle hooks) likewise now carry the signed-in user's resolved account scope, so `ctx.can()` there sees the same `@request.account.*` values as a REST request.
