### Security
- A relation into a tenant-owned collection now only accepts ids from the request's active account. On create and update, another account's id gets the same `400 validation_not_found` as an id that does not exist, for single and multi relations. For non-hidden fields, an update accepts the ids the row already stores (so re-sending a whole record never fails on a link the client did not add) and checks only the ids it adds. Hidden fields receive the scope check even for stored ids, and requests without an active account cannot add links to empty-owner targets. The check sees the values after `before_create`/`before_update` hooks, so a hook that sets a relation to another account's record now gets the same `400`; a hook that must link across accounts writes through `ctx.records()`. Before this, the relation check confirmed that another tenant's record id existed, and a stored link let that tenant's own delete remove (`cascadeDelete`) or clear the linking row. Superusers, `crossTenant` contexts and `ctx.records()` writes are not narrowed. The target's `viewRule` is not applied, so a non-tenant target such as `users` stays referenceable by id (#497).

### Features
- `zigbase doctor` has a new `cross-tenant-relations` check. It reports, one `warn` per relation field, existing links from a tenant-owned row to a record owned by another account, and stored multi-relation values that are not a JSON id array (which it cannot examine). The links are ones stored before the relation scope above existed, or by a superuser or server-side write. They are left in place. Rows whose tenant value is NULL or empty belong to no account and are not counted. If the scan itself fails, only this check reports `skipped`, with the error.
