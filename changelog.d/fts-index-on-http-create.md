### Fixes

- Collections created or changed through the collections API or the admin UI now get their full-text search index in the same transaction as the schema change. Previously only startup provisioning built it, so `?search=` on a collection created over HTTP answered 500 until the next restart, and changing which fields are searchable over HTTP left the index stale. Making a field searchable backfills existing rows; adding, removing or renaming a searchable field rebuilds the index; turning search off or deleting the collection drops it (deleting a SQLite collection no longer leaves its `<name>_fts` shadow table behind). A change whose index cannot be built fails as a whole, and in a `-Dfts5=false` SQLite build the API answers 400 instead of accepting a searchable field the server would refuse at the next start. (#507)
