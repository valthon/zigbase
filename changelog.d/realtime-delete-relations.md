### Fixes

- Realtime `delete` events now reach row-constrained subscribers on collections that have a relation field. A tenant member, an ability holder, or the owner under a rule such as `owner = @request.auth.id` used to receive create and update frames but no delete frame, and the server logged `realtime: dropped delivery on <collection>: Validation`. This affected SSE and WebSocket on SQLite and PostgreSQL, including every ability-guarded collection. Delete authorization still uses only the deleted record's snapshot, so a `viewRule` that traverses a relation (`owner.team = …`) is still not delivered for deletes. Multi-value fields in the snapshot (such as a multi-relation) are now also evaluated with their stored values, where before they were treated as empty, and a `viewRule` that compares a hidden field (such as `owner = @request.auth.id && archived = false` with `archived` hidden) now decides deletes from the field's stored value instead of never matching. The hidden value stays on the server; delivered delete frames remain id-only. The stored values decide even when a `beforeDelete` hook changes the record it is handed. Deletes sent with an `Idempotency-Key` are authorized the same way, and if the server cannot read the stored values the delete fails and rolls back instead of being decided from a partial record (#486).

### Security

- A realtime `delete` event is now authorized against the deleted record's stored values. Before, the snapshot used for that check had empty `created`/`updated` values, fixed-point numbers in their decimal form (`250.00` compared as `250`, not as the stored `25000`) and json scalars without their JSON encoding. A `viewRule` comparing one of those fields could therefore send the id of a deleted record to a subscriber who was not allowed to view it, for example `created < "2026-01-01 00:00:00"` or `price < 100`. It could also withhold the delete from a subscriber who was allowed.
- A queued realtime record event whose collection is removed before delivery is now dropped and logged. It used to be forwarded as a custom-topic message to any subscriber allowed on a topic of that name, record body included (#486).
