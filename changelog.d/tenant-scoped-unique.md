### Breaking
- On a tenant-owned base collection (`tenant_field` set), a field marked `unique` (other than the tenant field itself, which stays table-wide) is now unique **per tenant**: it is enforced as a composite `UNIQUE (<tenant_field>, <field>)` instead of across the whole table (#498). A table-wide unique answered `409` whenever any tenant held a value, so one request per guess told a member of one tenant what another tenant had stored, and any tenant could claim a value for every other tenant. Two tenants can now hold the same value. To keep a value unique across all tenants, declare a unique index on it (`.indexes = .{ .{ .name = "...", .fields = .{"slug"}, .unique = true } }`). Existing deployments are converged at startup, for `.collections` and collections created through the API alike: PostgreSQL swaps the constraints in place, and SQLite rebuilds each affected table once, keeping its rows and any migration-created indexes and triggers; a SQLite table the rebuild cannot reproduce is refused at startup instead (see Fixes). `zigbase import` upserts on such a field match the tenant and the key, so they never select another tenant's row; each such upsert row must carry a non-empty tenant value.
- Auth collections are excluded from unique-scope convergence at startup and on API updates. Their uniqueness behavior is unchanged: configured identity fields receive global partial unique indexes over non-empty values, and declared unique fields stay global. The default `["email"]` identity does not gain username uniqueness; existing duplicate non-empty usernames keep booting.

### Fixes
- SQLite rebuilds qualify migration-object drops with the main schema, preserving unrelated TEMP indexes and triggers with the same names.
- A SQLite table rebuild (startup convergence or a collections API update) no longer discards schema it does not own. It used to rebuild from the stored definition, dropping migration-added columns and any migration-created index or trigger that did not survive the copy. It now refuses, before changing anything, a table with a column, constraint or foreign key the engine does not create, or a view or trigger on another table that depends on it, and answers `400` with the offending column, clause or constraint and an explicit-migration instruction on collections API updates. It also answers `400` naming the object when a migration-created index, trigger or view depends on a column the update drops or renames, or when a migration trigger or view uses wildcard or positional dependencies and the update changes the column layout. Engine indexes and triggers are recognised by their SQL rather than their name and regenerated, and every other index and trigger is restored as it was (#498).
- Adding or changing `.tenant_field` on an existing collection in `.collections` is now persisted at startup. It was ignored before, so the collection stayed unscoped while the startup log reported it as tenant-owned.
- On PostgreSQL, updating a base collection through the API now adds or removes the unique constraint when a field's `unique` flag changes. It previously changed only the stored definition, leaving the column's uniqueness as it was. Auth collections retain their previous update behavior.

- PostgreSQL startup convergence compares constraint columns using physical 63-byte identifiers, so long field names neither retain legacy global uniqueness on base collections nor accumulate redundant tenant constraints. SQLite rebuilds refuse attached TEMP triggers before destructive DDL, preserving their behavior and the original table.

### Changed
- OpenAPI marks each unique field's scope (`x-zigbase-unique-scope`: `global` or `tenant`), and the admin schema editor shows it, with the tenant field, beside the unique checkbox (#498).
